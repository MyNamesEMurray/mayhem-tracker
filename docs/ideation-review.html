Where Mayhem Tracker Breaks at Ten Times the Size

Twenty findings across performance, design and features, measured against the live database rather than estimated. The headline: every visitor to the site downloads twenty-one patches of data to look at one.

Reviewed main @ ed991e7 (v2.14.4) Live dataset 137,317 games / 2,144 contributors / 21 patches Measured 28 Aug 2026
00

What I actually did

I read the ingest function, the migrations, the local database layer, both client data layers and both component trees, then measured the live Supabase project directly rather than reasoning about it. Every number below came back from the real API today.

That matters because the brief asked about "hundreds of concurrent users." You already have 2,144 contributors and 137,317 games. So this is not a hypothetical: it is a roughly ten-times-growth question against a real, working base. Several things that are comfortable today get uncomfortable at that size, and two of them get worse every single patch whether or not you grow at all.

Findings carry IDs because the sequencing section at the end refers back to them. Severity is my read of what happens if you never do it.

01

Performance and scale

Seven findings. The first is the biggest single win available anywhere in the codebase, and the fourth is the one that would keep me up at night.

P1 High Biggest measured win

Every visitor downloads all 21 patches to render one

The site's default view is the current patch. To draw it, fetchChampionStats() and fetchAugmentTotals() pull those views in their entirety, paged 1,000 rows at a time in parallel, across every patch ever recorded. The filtering then happens in the browser.

Difference 4.5× fewer21× fewer 20.3× smaller

Two things make this worse than a one-off inefficiency. It grows: each new patch adds roughly 372 rows and about 11 KB gzipped to what every visitor downloads, forever, and none of it is ever looked at by default. And the desktop app has the identical pattern in src/main/community.ts, softened only by a six-hour disk cache.

The fix is a query parameter. PostgREST already supports ?patch=eq.26.9, the patch list is available separately from community_patch_spans (21 rows), and the range picker already knows exactly which patches it wants. Older patches load when someone actually selects them.

Concern

The site's auto-widen feature reaches back through older patches when the current one is thin, so it needs more than the current patch sometimes. That makes this a lazy-loading change, not a one-line filter: fetch the current patch first, paint, then fetch older patches on demand. Worth doing properly rather than quickly, because a half-done version means a spinner appearing on a view that used to be instant.

Impact 20× less data over the wire per visit and 4.5× fewer round trips, so first paint stops waiting on 237 KB of JSON. At hundreds of concurrent visitors it is also a 20× cut in Supabase egress and PostgREST connection pressure. Stops the site getting measurably slower every patch.
P2 High Correctness, not speed

A game can be half-ingested, and nothing will ever fix it

The ingest function writes five tables in sequence, each its own HTTP round trip through PostgREST, with no transaction around them:

supabase/functions/ingest/index.ts, the write sequence

await supabase.from("matches").upsert(matchRows)              // succeeds
await supabase.from("match_participants").upsert(partRows)    // ← fails here
await supabase.from("match_participant_augments").upsert(...)  // never runs
await supabase.from("match_item_events").upsert(...)          // never runs
await supabase.from("contributions").upsert(contribRows)     // never runs

// The client got a 500 and stops, but the match row is already committed.
// It has no participants. It counts toward totals. Nothing retries it,
// because a later upsert of the same game hits ON CONFLICT DO NOTHING.

Today, with modest traffic, partial failures are rare. Concurrency is exactly what makes them common: connection exhaustion, statement timeouts and lock contention all rise together, and all of them can land between two of those statements. The result is silent, permanent, and invisible in any dashboard, because a match with no participants looks like a match.

The fix is one Postgres function, ingest_games(token, payload jsonb), doing all five inserts in a single transaction. The edge function keeps the validation it already does well and makes one RPC call instead of five upserts. All or nothing, which is what this data deserves.

Impact Eliminates a class of silent data corruption that gets more likely as you grow. Also cuts five network round trips per batch to one, which is a real latency win on the upload path as a side effect.
P3 High

Rate limiting counts an unbounded table on every upload

Every ingest request runs a count=exact over contributions filtered by token, plus a second windowed count if the first crosses the burst allowance, plus a third over quarantine. In Postgres, an exact count is not a lookup: it visits every matching row.

A contributor who has uploaded 800 games has 800 rows visited before their upload is even considered. That is fine. The problem is the shape: this is the hottest query in the system, it runs before any useful work, and it gets slower for every user as each user contributes more. At ten times the contributors, with more history each, it is the first thing to fall over.

The fix is a counter rather than a count. One contributor_stats row per token holding lifetime total, a rolling daily count with its window start, and pending-quarantine count, updated inside the same transaction as P2. The rate check becomes a single primary-key read.

Impact Turns three growing scans into one indexed read, on the request path that every uploaded game passes through. This is the difference between the upload endpoint degrading gracefully and degrading suddenly.
P4 High Do this first

The database cannot be rebuilt from this repository

There are six migration files. Across all of them there are zero create table statements. They create materialized views and indexes on top of tables that are only referenced, never defined.

Referenced by migrations, defined nowhere in the repository

public.matches                      public.contributions
public.match_participants           public.quarantine
public.match_participant_augments   stats.refresh_all()
public.match_item_events            the 30-minute refresh schedule
                                    every row level security policy

All of that exists only inside the live Supabase project. There is no way to stand up a staging copy, no way to test a schema change before it touches production data, no review trail for the policies protecting 137,317 games, and no recovery path that does not involve reconstructing the schema from memory.

This is not a performance finding, but it is first in the running order, because P2 and P3 both add database functions and I would not want to write either against a schema I cannot see, diff, or test.

supabase db pull writes the current state out as a migration. That is most of an afternoon, and it is the cheapest risk reduction on this page.

Impact No user-visible change. Makes every subsequent backend change reviewable and reversible, and makes a catastrophic loss recoverable rather than terminal.
P5 Medium

One materialized view is quadratic-ish and refreshes every 30 minutes

stats.matchup_coverage self-joins match_participants against itself across teams to count distinct champion pairs. Its own migration says to "expect this one to take a minute or two to build." Every game adds 25 cross-team pairs to distinct over, and it rebuilds on the same 30-minute schedule as everything else, behind the same advisory lock.

It produces one row, for one tile, on the community page. At ten times the games it plausibly runs long enough to start colliding with its own schedule and delaying every other aggregate behind the lock.

Two ways out, and I would pick the second: move it to a slower schedule of its own, or make it incremental by maintaining a champion_pairs table written during ingest. The second costs more but turns a growing full scan into a constant-time upsert, and it is the same table F2 below needs anyway.

Impact Protects the freshness of every other statistic on both surfaces from one expensive tile. Low user-visible value on its own; high value bundled with the matchups feature.
P6 Low Twenty minutes

The local database is missing the two indexes it filters on most

src/main/db.ts creates nine indexes. Neither games.game_version nor games.queue_id is among them, and both are filtered on constantly: applyPatchFilter emits game_version IN (...), applyQueueFilter emits queue_id = ?, and getMatchFilterOptions runs a SELECT DISTINCT over game_version every time the filter bar loads.

The patch range picker shipped in v2.14.2 made this hotter. A player with thousands of games scans all of them to populate a dropdown. synchronous is also left at FULL, where NORMAL is the standard pairing with WAL and is safe for this workload.

Impact Snappier filtering for players with long histories, which is precisely the engaged users you least want to annoy. Three lines, no risk, ships with any release.
P7 Low

The Supabase paging loop is written twice, again

fetchAll in website/src/lib/api.ts and fetchView in src/main/community.ts are the same forty lines: fetch page zero with a count header, fan the rest out with Promise.all, fall back to walking pages if the header is missing. Same fix as the patch picker and the scoring maths before it.

Worth folding into P1 rather than doing separately, since P1 rewrites both call sites anyway.

Impact One fewer place for the two surfaces to disagree about how they talk to the same database. Roughly 40 duplicated lines removed.
02

Design language

The token and component unification is largely done. What remains is one big thing, two small ones, and a genuine decision for you to make.

D1 Medium The remaining big one

The tier list is still two implementations of one table

Roughly 1,200 lines across four files draw the same two boards from the same data with the same scoring:

FileLinesSurface
website/src/components/ChampionsTable.tsx234Site
website/src/components/AugmentsTable.tsx329Site
src/renderer/pages/Champions.tsx289App
src/renderer/pages/Augments.tsx361App

They have already drifted. The app shows explicit Win Rate and Pick Rate columns; the site does not. The site has a mobile card layout below 700px and a SortControl for it; the app has neither, so a narrow window gets a horizontally cramped table. Neither difference was designed. They are just where two people stopped.

There are two honest ways to fix it.

Option A

Share the mechanism, keep the chrome

Extract a headless <StatTable> that owns sorting, tier assignment, the responsive card breakpoint and keyboard behaviour. Each surface passes its own column definitions and renders its own cells.

Nothing visible changes on either side. The app gains the mobile card layout for free because the shared component owns the breakpoint.

Lower risk. Removes maybe 500 of the 1,200 lines. The columns can still drift, because columns stay local.
Option B

One board, columns included

Share the whole thing, columns and all, taking the union rather than the intersection. The site gains the app's Win Rate and Pick Rate columns; the app gains the site's responsive cards and mobile sort control.

This is the rule that worked for SearchField and WinRateBar: when two versions disagree, ship the superset and let each call site opt out.

My recommendation. Removes closer to 800 lines, and makes the two boards genuinely the same board. Costs a real design decision on each column.

Concern

The two boards are not in identical situations. The site is a public tier list read by people who arrived from a search engine; the app is a tool open beside a game. Density that suits one may not suit the other, and sharing columns wholesale removes the freedom to tune that separately. I still recommend Option B, but the honest version of the recommendation is that you should look at the app at 1280px wide with all six columns before committing.

Impact Roughly 800 fewer lines and one board instead of two. Players get the same columns wherever they look, and the app stops breaking at narrow window widths.
D2 Low

The queue picker is the patch picker all over again

The app has QueueSelect.tsx, 48 lines. The site has an inline <select> in App.tsx with its own "All queues" option. Same control, same data, two spellings. This is the exact shape of the patch picker before v2.14.2, and the fix is the same: one shared component, each surface keeps its own state.

Impact An afternoon. Removes the last duplicated filter control.
D3 Low Ten minutes

There are three ItemIcons, and one is dead

Impact 67 lines gone, and item icons stop being able to drift between surfaces.
D4 Low

The app has no narrow-window behaviour

The site collapses its tables into labelled cards below 700px and swaps the sortable header row for a SortControl dropdown. The app does neither, so resizing the window narrow, which people do constantly when running a tracker beside a game, produces a cramped table rather than a designed layout.

This resolves itself under D1 Option B and does not otherwise need its own work. Listed separately because it is the most visible symptom of the duplication, and because it argues for Option B over Option A.

Impact The app becomes usable in a half-width window, which is how a second-screen tool actually gets used.
03

Features

Five ideas, ordered by how much they use data you are already collecting and currently throwing away. The first two need no new collection at all.

F1 Highest value

Tell players which augment to take, while they are choosing

This is the feature the product is one step away from and does not have.

The app already polls the Live Client Data API every five seconds during a game, tracking all ten players' items and augment pickups. It knows the gameflow phase, your champion, and the patch. Separately, it holds community augment win rates broken down per champion. Nothing connects the two.

Augments are the single highest-leverage decision in Mayhem, they are offered under time pressure three times a game, and the app is already open on the second monitor. A panel that says "on Ziggs this patch, these are the picks" is the answer to the question players actually have at the moment they have it.

Every element here already exists: the rarity palette, the rate meter, the small-sample rule, the score. This is assembly, not invention.

Concern, and it is a real one

I checked, and the public Live Client Data API does not expose which three augments you are being offered. So this cannot be "take the middle one." It has to be a ranked board for your champion that you glance at and match against your offer yourself.

That is still useful, but it is a weaker promise than it first sounds, and I would not build it believing otherwise. Reading the offered choices off the screen would mean image recognition or memory reading. Both are a different product with a different risk profile, and neither is something I would recommend for a tool that currently stays safely inside published APIs.

Impact Turns the app from a thing you review after a game into a thing you keep open during one. That is a different retention profile entirely, and it is the strongest argument for installing the app over bookmarking the site.
F2 Data already collected

Champion matchups, which you count but never analyse

stats.matchup_coverage exists solely to count how many champion pairs have faced each other, for a single tile. The underlying data, every cross-team pairing in 137,317 games with a known winner, supports the actual question: who beats whom.

No view exposes it. I checked for matchup_stats, champion_matchups and similar; all 404. This is a complete feature sitting in a table, one materialized view away.

It also solves P5: if you maintain a champion_pairs rollup incrementally during ingest, the expensive coverage count becomes a cheap sum over it, and the matchup feature is the same table read a different way.

Impact A genuinely new page on the site with real search traffic potential ("Ziggs vs Brand ARAM"), and a champion-page section answering the question players ask most. Pays for P5 rather than costing extra.
F3 Data already collected

Augment synergies

match_participant_augments stores every augment with its slot and participant. Which means every pair and triple a player actually ran together is recorded, with the win attached. Nothing computes it.

"Accelerating Sorcery plus Ultra Hydra wins 8 points above either alone" is the kind of finding that makes a stats site worth returning to, and it cannot be got anywhere else because nobody else is collecting Mayhem augment data at this grain.

Concern

Pair counts explode. With roughly 640 augments the pair space is around 200,000 combinations before champion breakdown, and most will be under-sampled. This needs a minimum-sample floor at least as strict as the existing one and probably strictest of all, or it will confidently report noise. Start with pairs only, never triples.

Impact Differentiating content nobody else has. Medium build cost, entirely on the aggregate side.
F4

Show players where they differ from the community

The app holds both your games and the community's, and the Champions page already has a toggle between them. What it does not do is put them side by side. "You win 44% on Lux; the community wins 53%" is more actionable than either number alone, and it needs no new data, no new aggregate and no backend work: both datasets are already in memory on the same page.

The natural home is the champion page, as a delta column or a second muted bar behind the community one.

Impact Makes the app's own data useful rather than merely present, and gives players a reason to care about their history beyond nostalgia. Small build.
F5

Tell contributors what they contributed

2,144 people have opted in to sharing games. The app can tell them their contributor ID and let them withdraw, which is the right ethical baseline, but it never tells them what their sharing produced.

"Your 340 games are part of the 5,612 behind this Ziggs number" closes the loop on an opt-in that currently feels like a one-way donation. It is a retention feature disguised as a courtesy, and it costs one count.

Impact Makes opting in feel like joining something. Cheapest feature here by a distance.
04

The order I would do this in

Sequenced by dependency first, then by value per unit of risk. The first three are all low-risk and two are nearly free.

Pull the schema into the repository

P4 · no user impact · half a day

Everything in the backend is safer afterwards and nothing is safe before it. supabase db pull, review what comes out, commit it. This is the prerequisite for steps 4 and 5, and it is the one item here whose absence could turn an incident into a catastrophe.

Add the two local indexes

P6 · app only · twenty minutes

Do it now because it is free, it ships with whatever release comes next, and it makes the patch range picker you just shipped feel the way it should for players with long histories.

Filter by patch at the source, and share the paging code

P1 + P7 · both surfaces · the biggest measured win

20× less data per visit, 4.5× fewer requests, and the site stops getting slower every patch. Do the lazy-load properly so auto-widen keeps working. Fold the duplicated paging loop into the same change, since it rewrites both call sites anyway.

Make ingest atomic, and count with counters

P2 + P3 · backend · needs step 1

One ingest_games() function, one transaction, one RPC call. Maintain the contributor counters inside it so the rate check becomes a primary-key read. These are one piece of work, not two, and together they are what makes the write path safe at ten times the volume.

Clear the small design debt

D2 + D3 · an afternoon

Delete the dead ItemIcon, point the app's three importers at the shared one, share the queue picker. Cheap, and it keeps the shared system from quietly re-accumulating the duplication you just spent weeks removing.

Unify the tier list

D1 + D4 · pick Option A or B first

The largest remaining design work. Look at the app at 1280px with all six columns before committing to Option B. Whichever you pick, the app gets narrow-window behaviour out of it.

Build the live augment panel

F1 · app only · no backend work

First feature, because it needs nothing new: the live session, the community augment rates and every UI component already exist. Ship it knowing it is a ranked board rather than a read of your actual offer.

Champion pairs: the rollup, then the feature

F2 + P5 · backend then both surfaces

Build the incremental champion_pairs table during ingest, which retires the expensive coverage view, then expose matchups on top of it. One piece of work that pays a performance debt and adds a page.

The rest, by appetite

F3, F4, F5

F5 is an hour and makes 2,144 people feel seen. F4 is small and makes the app's own data earn its place. F3 is the most interesting and the most likely to report noise if rushed, so it goes last.

05

What worries me

Consolidated, including the things that argue against my own recommendations.

The backend has no rehearsal space

This is the thread running through P2, P3, P4 and F2. Every one of them is a database change, and right now there is nowhere to make a database change except production, against a schema that exists nowhere but production. Until step 1 is done, I would treat every backend item on this page as blocked, not merely unstarted.

P1 can regress the experience if done carelessly

Downloading everything up front is slow, but it makes every subsequent interaction instant, because it is all in memory. Filtering at the source trades that for a request whenever someone widens the patch range. Done well, with the current patch loading first and the rest arriving in the background, it is strictly better. Done as a naive filter, it turns an instant control into a spinner.

Sharing components has a failure mode you have already hit once

When the site grew a second local search box because the shared one carried a clear button it did not want, that was the shared component being under-specified. D1 Option B is the same risk at four times the size: if the shared table cannot express what one surface needs, that surface forks and you end up with three implementations instead of two. Take the union deliberately.

F1 promises less than it appears to

Worth repeating because it is the feature most likely to be greenlit on the strength of the mockup. The app cannot see which three augments you were offered. It can only rank all of them. That is genuinely useful and it is not what "augment recommendations" sounds like.

F3 will confidently tell you things that are not true

Augment pair statistics over a 200,000-cell space built from 137,317 games will produce spectacular-looking results that are sampling noise. The existing Wilson score floor is the right tool and it needs to be applied harder here than anywhere else on the site, because the surface area for false discovery is an order of magnitude larger.

Two of these findings are mine

The dead ItemIcon in D3 and the duplicated paging loop in P7 are both things I left behind during the earlier unification work. Worth noting because it is the same failure that produced the duplication in the first place: a component gets shared, and the copy it replaced does not get deleted.

The short version: the write path has a correctness bug that concurrency will find, the read path moves twenty times more data than it needs, the database that holds all of it cannot be rebuilt from this repository, and there are two finished features sitting unqueried in tables you are already filling.
