Performance and correctness

P1 – P7

Fetch the patches being shown, not all of them

Both surfaces downloaded every patch ever recorded in order to render one, and the payload grew by about 11 KB with every patch Riot shipped, forever. The site now loads in stages: the patch list, then the newest patch, then the two more that auto-widen can reach, then anything a range actually asks for. The app does the same on a first launch.

First paint, rows 7,887→261
First paint, requests 9→2
Typical session 5.2× smaller
Found The first version asked for zero patches when the patch list itself was unreachable, because that fetch swallows its own failure and returns an empty list. An empty list means the view is down, not that there are no patches. It falls back to fetching everything now.

Commit a batch of games in one transaction

The ingest function wrote five tables as five separate calls with nothing around them, and ran three count(*) queries over a contributor's whole history beforehand. A failure after the first write left a match with no participants: counted in every total, contributing nothing, never retried. Both are fine until the system is busy, and being busy is exactly what breaks them.

Rate-limit check 3 counts, unbounded→1 key read
Partial writes possible yes→no
Verified Forcing a constraint violation on the fourth of five inserts left zero orphan matches, zero orphan participants and zero orphan contributions. A duplicate upload counts once. A batch over the daily limit is refused without writing anything. An end-to-end POST through the deployed function wrote 1 match, 10 participants, 20 augments, 20 item events and 1 contribution; a second identical POST moved no counter. All test rows removed and the totals confirmed back at 161,230 and 2,144.

The schema, in the repository

Seven applied migrations had never been committed, including the base schema. They are recovered and in supabase/migrations/ now, with the review pipeline's live secrets stripped out and a note explaining what to seed instead.

Correction The review said the tables had been created by hand. They had not: the database had thirteen recorded migrations and the repository had six. The base schema was migrated properly; the files just were not committed.

The bug that was already there

not in the review

Half the rollup refreshes have been failing, for days

The database's statement_timeout is two minutes and pg_cron inherits it. stats.refresh_all() opened by setting that to zero, which reads as handling it and does not: the timer for the statement calling the function is armed before the function starts, and changing the value from inside the call it is already running does not re-arm it. So a full pass has always had two minutes, whatever the function said.

cron.job_run_details shows it dying at exactly 120 seconds on roughly every other run, as far back as the history goes. The fix is that the setting has to be its own statement, ahead of the call. A pass also used to abort on the first view that failed, leaving every view after it stale; failures are collected and raised at the end now, so one slow rollup costs its own refresh and nobody else's.

Time a pass was given 120s, then killed→as long as it needs
Next scheduled pass 163s, succeeded
One failure costs every later view→itself
Proven The 19:30 pass after the fix ran 163 seconds and completed — 43 seconds past the wall every run before it had hit — rebuilding all eight rollups, including the two new ones. Comfortable inside a half-hour slot.
Note The data was never wrong. Both heavy rollups match their source tables exactly for the current patch, because the passes that did complete caught everything up. But half the work was being thrown away, and two more rollups would have made that worse rather than better.

One tier list instead of two

D1 – D4 · option B

Four boards became one, columns included

The app and the site each had their own champions board and their own augments board: about 1,450 lines drawing the same two tables from the same numbers with the same scoring, drifted in ways nobody chose. A board is a list of columns now; each column says how to draw its cell, what to sort it by, and where it lands when the table becomes cards.

The columns are the union. The site gains Kills, Deaths, Assists and Gold; the app gains the card layout it never had. Thirteen columns do not fit a 1280px window, so Kills, Deaths and Assists get columns of their own only from 1400px — the only three that can be held back without losing anything, because the KDA cell beside them prints the same numbers at every width.

Window minimum 900px→720px
Card-layout CSS 177 lines, by index→one shared block
Net lines about 80 more
Verified Checked in a browser at 1600, 1280, 900 and 680px on both surfaces: the right columns appear and disappear, rows become grids with their figures labelled, the sort control appears exactly where the header row goes, every column sorts both ways, tier sorts S+ first with score breaking ties, and no page overflows sideways at 680.

Five features

F1 – F5

Tell players which augment to take, while they are choosing

The app polls the game's live data every five seconds and already knew the champion being played. It separately held community augment win rates per champion. Nothing connected the two. An In game tab now appears while a game is running and shows the best augments for your champion, split by rarity, with the ones you have already taken struck off — the app can see those, because an augment reveals itself by replacing a summoner spell's name.

What it is not: the live API does not expose which three augments you are being offered. This is the board you glance at and match your offer against, and the page says so rather than implying more.

Verified Rendered against the built app: three rarity columns of eight, taken augments leaving the list, one column at 720px, the fallback while the champion is still unknown, the redirect and vanishing tab when the game ends, and the auto-open firing from Overview but not from Settings.

Who beats whom

Every cross-team pairing in every game has been in the database since the first upload. One thing read it: a view counting how many distinct pairs existed, for a single tile. That count cost a self-join over 1.37 million rows every half hour and answered one number. Both champion pages now have a Matchups panel, and the tile is a cheap sum over the rollup that feeds it.

Coverage tile 6.1s→0.3s
Rollup 491,730 rows · 55 MB
Rebuild 18.7s, concurrent

The ranking needed a second statistic. Score is the floor of the confidence interval, right for best-first and quietly wrong for worst-first: it sinks a thin sample toward zero, so “struggles against” would fill with whichever opponents had been met eight times and lost to. The bad side ranks by the ceiling instead — the win rate a record cannot rule out — so a matchup has to be losing on its best reading to appear there.

Measured Brand, last three patches. By the ceiling his worst matchups are Sett at 43.6% over 429 games, Yunara over 421, Twitch over 493. Ranked by Score ascending they would have been Evelynn over 91 games, Fiora over 80, Kled over 86 — thinner samples with wider intervals, displacing matchups with five times the evidence.

Which augments work together

Augments are stored per participant with their slot, which means every combination anyone has actually run has been recorded with the win attached. Nothing computed it, and nobody else collects Mayhem augments at this grain. Expanding an augment on either surface now shows what it pairs well with.

The number that matters is not the pair's win rate — that is mostly the win rate of whichever half is stronger. It is the lift: how far the pair beats its own better half, measured from the floor of the pair's interval rather than its observed rate, so a pairing has to be proven better rather than merely luckier.

Rollup 98,586 rows · 12 MB
Distinct pairs 21,221
Grain pairs only, never triples
Measured Top of the live list: Big Brain with DropBear, 70.8% over 154 games, 6.5 points above either alone. Draw Your Sword with Upgrade Infinity Edge sits fourth on +4.2 despite a lower raw rate, because 1,740 games say so. Ranking by raw rate would have put High Roller with Combusting Interest third at 66.1%, where the lift is only +2.8 because High Roller is already 54.2% on its own.

Your record against everyone's, and what you contributed

The app has held both numbers for as long as it has had a community source and offered a switch between them, which meant you could see either and never both. The champion page now says it in one line — and says nothing of the kind under twenty games, because a difference between two win rates is a claim about both.

The same panel closes the loop on the opt-in. 2,144 people share their games; the app could tell them their contributor id and let them withdraw, which is the right baseline and still a one-way donation. It now says how many of the games behind the number are theirs, counted from accepted uploads only.

Rendered “33 of your Ziggs games are in the 5,612 behind these numbers. You: 41 games, 43.9%. Community: 5,612 games, 53.0%. 9.1 points below the community on Ziggs, over 41 games.”

Where the review was wrong

4 corrections

D1 — the columns that had drifted

The review said the app showed Win Rate and Pick Rate columns and the site did not. The site had both. The real drift was Kills, Deaths, Assists and Gold, which only the app had, and the card layout, which only the site had.

D1 — the line count

The review estimated roughly 800 fewer lines. The change is about 80 lines more. The duplication is genuinely gone — one board, one comparator, one card layout — but each column now declares its sorting and its card placement rather than implying them, and the shared code carries the reasoning. The point was never the line count.

D3 — the dead ItemIcon

The review said website/src/components/ItemIcon.tsx had zero importers and could be deleted. It is live. ChampionDetail.tsx imports it as "./ItemIcon", which the search that produced the finding missed. Both local ItemIcons are correct minimal adapters over the shared component. No change made.

P4 — how the schema got there

The review said tables had been created by hand in the dashboard. Thirteen migrations were on record in the database against six in the repository. The schema was migrated properly; seven files were simply never committed.

One thing for you

action

Live secrets sit in the database's own migration history

The quarantine_review_pipeline migration seeded admin_config with real values inline: the secret that authorises approve and deny links, the cron secret, an API key and a personal email address. They have never been in git and the copy committed now has them removed — but they are still in the project's migration history, which means supabase db pull writes them straight into a working tree. Worth rotating, and worth knowing before anyone pulls.
